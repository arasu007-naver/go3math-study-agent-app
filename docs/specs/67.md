## 배경과 목적
실황 수업 화면은 TopicLiveClassScreen(`app/topic-live-class.tsx`)과 HotlineClassScreen(`app/hotline-class.tsx`)입니다. 캔버스는 TopicLiveCanvas(`src/kit/canvas/note-canvas/topic-live-canvas.tsx`)와 HotlineClassCanvas(`src/kit/canvas/note-canvas/hotline-class-canvas.tsx`)이고, 둘 다 같은 WebView 템플릿 `src/kit/canvas/templates/live-class-canvas-template.ts`를 씁니다.

새 메시지가 오면 패널은 `playToPointInternal(guide, lastGuide)`를 호출합니다. 그러면 `@qoolla/script-parser`의 `playToPoint`가 현재 컷부터 목표 컷까지 컷을 하나씩 webview에 보냅니다. 중간에 리셋 컷(CLEAN/CLEAN_SCENE/CLEAR)이 여러 개 있으면 CLEAN이 제때 적용되지 않습니다. CLEAN이 맨 끝에 적용된 것처럼 동작해서, tutor-web 실황 보드와 같아야 할 마지막 내용이 지워집니다.

코드에서 확인한 원인은 다음과 같습니다.
1. 템플릿 `clearCanvas`(CLEAR_CANVAS/CLEAN/CLEAR/CLEAN_SCENE)는 `toDataURL`을 동기로 실행한 뒤 `setTimeout(60)` 안에서 그 시점의 캔버스 객체를 지웁니다(backgroundSubs 제외).
   - `toDataURL`이 오래 걸리면 RN의 `sleep(120)`이 소용없습니다. WebView JS 스레드가 바쁜 사이 다음 ADD 메시지가 큐에 쌓입니다. 그 ADD의 `setTimeout(10)`이 60ms 삭제 타이머보다 먼저 돌아서, CLEAN 뒤에 그려진 객체까지 지워집니다.
   - `toDataURL`이 예외(예: tainted canvas)를 던지면 삭제 자체가 일어나지 않습니다.
2. 리셋 이전 컷이 남긴 지연 추가 작업이 리셋 뒤에 캔버스에 객체를 다시 넣습니다. 대상은 다음과 같습니다.
   - `addObjToCanvas`의 `fabric.util.enlivenObjects` 콜백(이미지는 로드가 끝나야 호출됨)
   - `showSyncMembers`(360ms+96ms 뒤)
   - PROLOGUE/FOLLOW/EPILOGUE의 `setTimeout(10)`
   - `showEpilogues`/`showPrologues`, `importObjectFromClipboard`, `syncCanvasObjects`의 enliven 콜백
   그래서 리셋이 안 된 것처럼 보입니다.
3. RN 쪽에서 `ctx.playToPoint`와 'canvas-synch'는 fromPt로 렌더 클로저의 `lastGuide` state를 넘깁니다. 앞선 재생이 `playChainRef`에서 아직 진행 중일 때 다음 메시지가 오면, 이 fromPt는 낡은 지점입니다. 그 결과 이미 실행한 리셋 컷과 그 앞뒤 컷이 다시 재생되고, 재생 끝에 보낸 SYNCH 객체도 다시 리셋됩니다.

목적: 컷이 몇 개든, 리셋 컷이 몇 번 섞이든 webview 캔버스의 최종 상태가 컷 순서대로 실행한 결과와 같게 합니다. 즉 마지막 리셋 컷 뒤의 객체만 남고, backgroundSubs 객체는 유지됩니다.

## 범위
하는 것
- `live-class-canvas-template.ts`의 리셋 처리를 동기 즉시 삭제로 바꿉니다.
- 템플릿에 리셋 세대(epoch) 가드를 넣어, 리셋 전에 시작된 지연 추가 작업이 리셋 뒤 캔버스에 객체를 넣지 못하게 합니다.
- TopicLiveCanvas와 HotlineClassCanvas의 `runPlay`가, 재생을 시작하는 시점에 실제로 마지막으로 재생을 마친 지점(`lastPlayedRef`)을 fromPt로 쓰게 합니다.
- 위 동작을 검증하는 jest 테스트를 추가합니다.

하지 않는 것
- `@qoolla/script-parser`(qoolla-package)의 `playToPoint`/`fastforward` 로직과 버전은 바꾸지 않습니다.
- 진입 재생(가까운 리셋 컷부터 fastforward), CLASS_ON_AIR 재시작, 'follow'(synchToCurrent, force), 'lastStep', 퀴즈, 스냅샷 동작은 바꾸지 않습니다.
- CLEAN_BOARD(`resetCanvas`), CLEAN_MY_MEMO, CLEAN_ADHOCS의 동작은 바꾸지 않습니다.
- 리셋 때 SAVE 스냅샷을 RN에 올리는 기존 부수효과는 유지합니다(전송 시점만 즉시로 바뀜).
- topic-canvas-template.ts, whiteboard-canvas-template.ts, 서버 메시지 형식은 바꾸지 않습니다.

## 변경할 동작
### 1. WebView 템플릿 (`src/kit/canvas/templates/live-class-canvas-template.ts`)
1. 전역 변수 `var resetEpoch = 0;`을 추가합니다.
2. `clearCanvas`를 다음 순서로 동기 처리합니다.
   - `resetEpoch += 1`
   - `toDataURL`을 try/catch로 감쌉니다. 성공하면 `{content: dataUrl, contentMeta:'SAVE'}`를 postMessage하고, 실패하면 건너뜁니다.
   - 그 자리에서 `canvas.getObjects()` 가운데 id가 `backgroundSubs`에 없는 객체를 모두 `canvas.remove`합니다.
   - `canvas.renderAll()`
   - 삭제를 미루는 `setTimeout`은 없앱니다.
3. 지연 추가 경로는 작업을 시작할 때 `const epoch = resetEpoch`를 잡아 둡니다. 실제로 `canvas.add` 하기 직전에 `epoch !== resetEpoch`이면 추가하지 않고 버립니다. 해당 경로:
   - ADD/MODIFY의 `setTimeout(addObjToCanvas)`와 `addObjToCanvas` 안의 enliven 콜백
   - `showSyncMembers`의 enliven과 `setTimeout(96)`
   - PROLOGUE/FOLLOW/EPILOGUE의 `setTimeout(10)`과 그 안의 addObjToCanvas
   - `showPrologues`, `showEpilogues`, `importObjectFromClipboard`(FLY), `syncCanvasObjects`(SYNCH)의 enliven 콜백과 setTimeout
   - `exeObjMovingAnimation`(ON_ANIMATION)
   이미 시작된 애니메이션 객체가 리셋으로 지워진 경우에는 애니메이션 콜백에서 추가 렌더 말고 다른 부작용이 없어야 합니다.
4. BACKGROUND/NOTEBOOK/INIT_BACKGROUND처럼 `canvas.clear()`를 부르는 배경 전환에서도 `resetEpoch += 1`을 해서, 이전 지연 추가 작업이 새 배경 위에 그려지지 않게 합니다.
5. dispatchCanvasAction의 분기(`case 'CLEAR_CANVAS': case 'CLEAN': case 'CLEAR': case 'CLEAN_SCENE':` → clearCanvas)는 문자열을 그대로 유지합니다. 기존 테스트 정규식 `/case 'CLEAR_CANVAS':\s*case 'CLEAN':\s*case 'CLEAR':/`를 계속 통과해야 합니다.

### 2. TopicLiveCanvas / HotlineClassCanvas (두 파일에 똑같이 적용)
1. `runPlay(targetPt, fromPt, opts)`의 비진입 분기(`fromPt != null && hasPlayedSinceLoadRef.current`)를 바꿉니다. `opts.force`가 아니고 `lastPlayedRef.current`가 있으면, 넘겨받은 fromPt 대신 `lastPlayedRef.current`(`{studyIdx, step}`)를 fromPt로 써서 `playToPoint`를 호출합니다. 이 값은 `playChainRef` 직렬화로 앞 재생이 끝난 뒤 읽히므로 실제 진행 지점입니다. force 호출(synchToCurrent, CLASS_ON_AIR)은 지금처럼 넘겨받은 fromPt를 씁니다.
2. `runCut`의 리셋 컷 뒤 `await sleep(120)`은 유지합니다(템플릿 수정 뒤에도 남겨 두는 안전 여유).
3. 나머지 흐름은 그대로 둡니다: 진입 재생의 fastforward, 중복 목표 건너뛰기, 재생 뒤 targetPt.objects SYNCH 전송.

### 3. 테스트
- 템플릿 동작 테스트(예: `__tests__/liveClassResetOrder.test.ts`)를 추가합니다.
  - `liveClassCanvasTemplate(1280, 1900, 'orange', 6)`가 만든 HTML에서 마지막 인라인 `<script>` 본문을 꺼내 `new Function`으로 실행합니다. 이때 가짜 `fabric`, `window`, `document`, `navigator`, `ReactNativeWebView`를 주입합니다.
    - 가짜 Canvas는 add/remove/getObjects/toDataURL/renderAll/requestRenderAll/clear/setBackgroundImage/on/setDimensions/freeDrawingBrush/discardActiveObject를 갖습니다.
    - 객체는 animate/bringToFront/moveTo를 갖습니다.
    - `util.enlivenObjects`는 테스트가 지연을 조절할 수 있게 만듭니다.
  - `dispatchCanvasAction`을 돌려받아 jest fake timers로 검증합니다.
- `__tests__/classOnAirEntryReplay.test.tsx` 형식으로 RN 패널 테스트를 추가해 fromPt 동작을 검증합니다.

## 수용 기준
- 템플릿 테스트: `ADD a` → `CLEAN` → `ADD c`를 시간 간격 없이 연달아 dispatch하고 타이머를 모두 돌리면, 캔버스 객체 id 목록은 `['c']`입니다.
- 템플릿 테스트: enliven 콜백을 늦춘 `ADD a`를 dispatch합니다. 콜백 전에 `CLEAN`을 dispatch한 뒤 콜백과 타이머를 모두 돌리면 캔버스에 `a`가 없습니다.
- 템플릿 테스트: syncMembers에 `sync:a:1`이 있는 상태에서 `ADD a`를 실행하고, 200ms 뒤(showSyncMembers 실행 전) `CLEAN`을 dispatch합니다. 타이머를 모두 돌리면 캔버스에 `a`와 `sync:a:1`이 모두 없습니다.
- 템플릿 테스트: `ADD a`, `CLEAN`, `ADD b`, `CLEAR`, `ADD c`, `CLEAN_SCENE`, `ADD d`, `ADD e`를 연달아 dispatch하고 타이머를 모두 돌리면, 캔버스 객체 id 목록은 `['d','e']`입니다.
- 템플릿 테스트: BACKGROUND_SUBS로 `['paper']`를 설정하고 `ADD paper`, `ADD a` 뒤 `CLEAN`을 하면 `paper`는 남고 `a`는 지워집니다.
- 템플릿 테스트: CLEAN을 dispatch하면 타이머를 진행하지 않아도 같은 호출 안에서 리셋 대상 객체가 이미 지워져 있고, `contentMeta:'SAVE'` 메시지가 postMessage됩니다.
- 템플릿 테스트: 가짜 `toDataURL`이 예외를 던져도 CLEAN이 예외 없이 끝나고, 리셋 대상 객체는 지워집니다.
- 템플릿 테스트: enliven을 늦춘 `PROLOGUE x`/`FOLLOW y`/`EPILOGUE z`/`FLY f`/`SYNCH [s]` 뒤에 `CLEAN`을 하고 모두 진행하면, 캔버스에 x, y, z, f, s가 없습니다.
- 템플릿 테스트: CLEAN 뒤에 dispatch한 ADD/PROLOGUE/FOLLOW/EPILOGUE/FLY/SYNCH 객체는 정상적으로 캔버스에 추가됩니다.
- 패널 테스트(topic, hotline 각각): studySequences `[BACKGROUND(0), ADD a(1), CLEAN(2), ADD b(3), CLEAN(4), ADD c(5), ADD d(6), CLEAN(7), ADD e(8)]`로 {studyIdx:3, step:'main'}까지 재생합니다. 그 재생이 끝나기 전에 `ctx.playToPoint({studyIdx:6})`와 `ctx.playToPoint({studyIdx:8})`를 연달아 호출합니다. 재생이 모두 끝나면 webview로 보낸 메시지에서 두 번째·세 번째 재생은 각각 4~6, 7~8 컷만 보내고, `CLEAN`은 인덱스 4와 7에서 한 번씩만 다시 보냅니다(2번 CLEAN과 ADD a·b를 다시 보내지 않음).
- 패널 테스트: 위 상황에서 webview로 보낸 마지막 리셋 컷 메시지 뒤에 `ADD:e`가 있습니다.
- 기존 `__tests__/classOnAirEntryReplay.test.tsx`, `__tests__/classOnAirCanvasBehavior.test.tsx`, `__tests__/liveClassCanvasTemplate.test.ts`, `__tests__/canvasEraser.test.ts`를 포함한 jest 테스트가 모두 통과하고, `npx tsc --noEmit`에 새 오류가 없습니다.

## 가정
- 요구사항의 '실황 수업 스크린'은 TopicLiveClassScreen의 TopicLiveCanvas로 봅니다. 같은 템플릿과 같은 재생 코드를 쓰는 HotlineClassCanvas에도 똑같이 적용합니다.
- 리셋 컷 뒤에 지연 추가 작업이 객체를 넣는 것은 컷 순서상 리셋 전에 시작된 작업이므로, 버리는 것이 올바르다고 봅니다.
- 배경 전환(BACKGROUND/NOTEBOOK/INIT_BACKGROUND)도 리셋 세대를 올리는 것이 tutor-web 보드와 같은 결과라고 봅니다.
- SAVE 스냅샷을 60ms 늦추지 않고 즉시 보내도 RN의 업로드(uploadWorkoutToStorage)에는 영향이 없다고 봅니다.
