# 실황 수업 진입 재생을 정해진 간격으로 한 번만 하기 (TopicLiveCanvas / HotlineClassCanvas)

## 배경과 목적
학생이 실황 수업에 들어오면 lastcut(마지막 guide `{studyIdx, step}`)까지 칠판을 따라잡습니다. 이때 컷마다 정해진 간격으로 차례로 보여야 하는데, 지금은 한꺼번에 그려진 것처럼 보입니다. 관련 컴포넌트는 다음과 같습니다(docs/COMPONENTS.md 기준).
- 화면: **TopicLiveClassScreen** `app/topic-live-class.tsx`, **HotlineClassScreen** `app/hotline-class.tsx`
- 패널: **TopicLiveCanvas** `src/kit/canvas/note-canvas/topic-live-canvas.tsx`, **HotlineClassCanvas** `src/kit/canvas/note-canvas/hotline-class-canvas.tsx`

코드에서 확인한 원인은 다음과 같습니다(TopicLiveCanvas 기준, HotlineClassCanvas도 같은 구조).
1. 간격이 빠진 곳이 있습니다. `playToPointInternal`(388행)의 진입 분기는 `menuScript.backgroundCut`을 보내자마자 `fastforward`를 호출합니다. 패키지 v1.5.0의 fastforward는 curtains, 리셋 컷, BACKGROUND 컷 뒤에 기다리지 않습니다.
2. 진입 재생이 겹쳐 돕니다. 한 번 진입할 때 `playToPointInternal`을 부르는 경로가 여러 개입니다. `useEffect([menuScript])`의 syncPoint 재생(651~655행), WebView onLoad의 `initBackground`(500~505행), `loaded()`가 부르는 `onReceiveGuide(lastPoint)`, 화면의 `callGetLastTopicMessage` → `onReceiveGuide` → `ctx.playToPoint`가 있습니다. 이 호출들은 await 없이 동시에 시작될 수 있습니다. 게다가 `hasPlayedSinceLoadRef`는 재생이 끝난 뒤에야 true가 되므로, 앞선 fastforward가 도는 동안 들어온 호출도 다시 fastforward로 갑니다. 그 결과 두 재생의 보드 액션이 섞여 간격이 무너집니다.

## 범위
### 하는 것
- `package.json`의 `@qoolla/script-parser`를 `github:arasu007-naver/qoolla-package#v1.6.0`으로 올리고 `package-lock.json`을 갱신합니다.
- 두 캔버스에서 backgroundCut을 보낸 뒤 `await sleep(CATCH_UP_GAP_MS)`를 합니다. 상수는 `./script-maker`(패키지 `export *` 재export)에서 가져옵니다.
- 두 캔버스의 `playToPointInternal` 실행을 직렬화합니다. 이전 재생이 끝나야 다음 재생이 시작됩니다.
- 이미 끝났거나 진행 중인 재생과 목표가 같은 중복 재생 요청은 건너뜁니다.

### 하지 않는 것
- `runCut`/`runPrologue`/`runEpilogue`/`runCurtains` 콜백 내용과 그 안의 `sleep(120)`은 바꾸지 않습니다.
- 수업 중 실시간 진행(`playToPoint` 순차 재생)의 대기는 바꾸지 않습니다.
- WebView 템플릿(`src/kit/canvas/templates/live-class-canvas-template.ts` 등), 화면 파일(`app/*.tsx`), 서버 메시지 형식은 바꾸지 않습니다.
- quiz/imageQuiz/snapshot/canvas-synch/synch guide의 처리는 바꾸지 않습니다.

## 변경할 동작
두 캔버스 파일에 똑같이 적용합니다.
1. ref 두 개를 추가합니다. `playChainRef = useRef<Promise<void>>(Promise.resolve())`, `lastPlayedRef = useRef<{studyIdx:number; step:string} | null>(null)`.
2. `playToPointInternal(targetPt, fromPt?, opts?: { force?: boolean })`는 실제 재생 함수 `runPlay`를 `playChainRef.current = playChainRef.current.then(() => runPlay(...)).catch(() => {})`로 이어 붙이고, 그 promise를 반환합니다. 그래서 두 재생이 동시에 돌지 않습니다.
3. `runPlay`는 실행 시점에 다음 순서로 판단합니다.
   - `studySequences`가 비어 있으면 아무것도 하지 않습니다(기존과 같음).
   - 중복 건너뛰기: `!opts?.force`, `hasPlayedSinceLoadRef.current === true`, `targetPt.action`이 `refresh`나 `synch`가 아니고 `targetPt.sync !== true`이며, `lastPlayedRef.current`의 studyIdx·step이 `targetPt`의 studyIdx·(step||mode||'main')과 같으면 재생하지 않습니다. 이때 `targetPt.objects`가 배열이면 SYNCH만 보냅니다.
   - 진입 재생(`fromPt == null || !hasPlayedSinceLoadRef.current`): backgroundCut이 있으면 보내고 `await sleep(CATCH_UP_GAP_MS)`를 한 뒤 `await fastforward(studySequences, targetPt, callbacks)`를 호출합니다.
   - 그 밖에는 기존처럼 `await playToPoint(studySequences, targetPt, fromPt, callbacks)`를 호출합니다.
   - 끝나면 `hasPlayedSinceLoadRef.current = true`, `lastPlayedRef.current = { studyIdx: targetPt.studyIdx ?? 0, step: targetPt.step || targetPt.mode || 'main' }`로 두고, 기존처럼 `targetPt.objects` SYNCH를 보냅니다.
4. 스크립트를 새로 로드할 때(`initClassBoard`, `reloadScript`에서 `hasPlayedSinceLoadRef.current = false`를 하는 곳) `lastPlayedRef.current = null`도 함께 합니다.
5. 강제 재생이 필요한 두 호출에는 `{ force: true }`를 넘깁니다. 하나는 같은 스크립트에서 받은 CLASS_ON_AIR의 처음부터 재생 `playToPointInternal({ studyIdx: 0, step: 'main' }, null, { force: true })`이고, 다른 하나는 `synchToCurrent`(follow)의 재생입니다.
6. 결과적으로 진입 화면에는 배경 → 180ms → (curtains → 180ms) → 시작 리셋 컷 → 180ms → 각 컷의 prologue/main/epilogue(각각 기존 대기 + 180ms)가 한 번만 차례로 보입니다.

## API 계약
외부 API 변경은 없습니다. 쓰는 패키지 계약은 `@qoolla/script-parser` v1.6.0입니다.
- `CATCH_UP_GAP_MS = 180`을 export합니다.
- `fastforward(cuts, targetGuide, callbacks)`는 칠판을 바꾸는 콜백(runCurtains, runCut, runPrologue, runEpilogue, runMagnifier)을 실행한 뒤마다 `callbacks.sleepFn(180)`을 호출합니다(기존 420/480/600ms 대기는 유지). 시그니처와 반환값은 v1.5.0과 같습니다.
- 서버 메시지(`lastLiveTopicMessage.content` guide `{scriptId, sourceType, sourceId, studyIdx, step}`) 형식은 바뀌지 않습니다.

## 수용 기준
1. `package.json`의 `@qoolla/script-parser`가 `github:arasu007-naver/qoolla-package#v1.6.0`이고, `package-lock.json`이 이 태그로 갱신되어 있습니다.
2. `npx tsc --noEmit`과 기존 jest 테스트 전체가 통과합니다. 기존 테스트의 sleep 순서 기대값이 새 간격 때문에 바뀌었다면 새 순서에 맞게 고칩니다.
3. TopicLiveCanvas에 studySequences `[BACKGROUND(0), ADD a(1), CLEAN(2), ADD c(3), ADD d(4)]`와 backgroundCut을 로드하고 `{studyIdx:4, step:'main'}`로 진입 재생합니다. sleep과 postMessage를 mock으로 기록하면 `postMessage(backgroundCut)`, `sleep180`, …, `postMessage(CLEAN)`, …, `sleep180`, `postMessage(ADD c)`, `sleep420`, `sleep180`, `postMessage(ADD d)`, `sleep420`, `sleep180` 순서가 관찰되고, ADD a는 보내지지 않습니다.
4. 3번에서 서로 다른 컷이나 step에 속한 보드 액션 두 개 사이에는 언제나 `sleep(180)` 호출이 한 번 이상 있습니다.
5. 3번 상태에서 `playToPointInternal({studyIdx:4, step:'main'})`을 await 없이 두 번 연달아 호출합니다(syncPoint 재생과 onReceiveGuide가 겹치는 상황을 흉내 냅니다). 이때 `fastforward`는 한 번만 호출되고, `postMessage(ADD d)`도 한 번만 관찰됩니다.
6. 진입 재생이 끝나기 전에 `ctx.playToPoint`로 `{studyIdx:5, step:'main'}`이 오면, 그 재생은 진입 재생의 마지막 보드 액션 뒤에 시작합니다. 두 재생의 보드 액션이 섞여 나오지 않습니다.
7. 진입 재생을 마친 뒤 `{studyIdx:5}`가 오면 지금처럼 `playToPoint(studySequences, …)`로 순차 재생되고, 그 재생 중에는 `sleep180`이 호출되지 않습니다.
8. 진입 재생을 마친 뒤 같은 스크립트로 CLASS_ON_AIR가 오거나 `follow` guide가 오면, 목표가 직전과 같아도 재생이 다시 실행됩니다(force).
9. 스크립트를 다시 로드(`reloadScript`/`initClassBoard`)한 뒤 같은 목표로 요청하면 다시 진입 재생(fastforward)이 실행됩니다.
10. quiz, imageQuiz, snapshot, canvas-synch, synch, lastStep guide의 처리 결과(호출되는 함수와 보내는 보드 액션)는 변경 전과 같습니다.
11. HotlineClassCanvas에서도 3번부터 10번까지가 똑같이 성립합니다.

## 가정
- '정해진 시간 간격'은 기존 고정 대기(480/420/480/600ms)에 컷·step 사이 최소 간격 180ms를 더한 것으로 해석했습니다.
- 중복 재생 판단 기준은 studyIdx와 step(step||mode||'main')이 같은지로 정했고, refresh, synch, sync:true guide는 중복으로 보지 않습니다.
- backgroundCut이 없으면 앞쪽 180ms 대기는 넣지 않습니다.
- 화면 쪽 진입 호출 경로(syncPoint, loaded, callGetLastTopicMessage)는 그대로 두고, 패널 안의 직렬화와 중복 제거로 겹침을 막습니다.
